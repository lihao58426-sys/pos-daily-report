# Agent 架构与生产化笔记

> 从本项目（POS 智能问答 Agent）出发，讲清一件事：
> **我们做的 Agent 和"生产级 Agent"之间，是程度差异，还是道路差异？——程度差异。**
> 本文把业界解决"模型表达力受限"问题的方案，按从近到远拆成三层，全部落到本项目的代码和踩坑上。

---

## 一、我们做的东西在坐标系里的位置

本项目拆开是四块：

1. **工具注册表**（`agent_tools.py` + `agent_tools_rfm.py`）：把 10 个数据库查询封装成"说明书"——函数名、功能描述、参数含义。LLM 只能看到这份清单。
2. **LLM 决策器**（`agent_llm.py`）：把"问题 + 工具清单 + 系统提示词"发给 DeepSeek，让它选择：*直接回答* 或 *要求调工具*。
3. **执行循环**（`agent.py`）：`run_agent` 每轮"LLM 想 → 调工具 → 结果塞回对话 → 再让 LLM 想"，直到它不再要求调工具（上限 5 轮）。
4. **数据层**（`database.py`）：SQLite 文件，bind-mount 进容器。

这个骨架在业界叫 **ReAct（Reasoning + Acting）** 或 **工具调用型 Agent（tool-calling agent）**。ChatGPT 插件、各家"AI 数据助手"，骨子里是同一个循环。差别不在骨架，在骨头上长了几层肉。

---

## 二、根本规律：模型的自由度上限 = 工具 × 描述 × 上下文

> **LLM 不能表达"我们没让它能表达"的东西。**

模型不是能凭空存取数据库的实体。它只能：读我们给的文本（系统提示词 + 对话 + 工具说明），然后在给定候选动作里**选一个并填参数**。于是：

- **工具清单**决定"能做什么动作"
- **工具描述**决定"什么情况下想起这些动作"
- **系统提示词**决定"知道多少背景事实"（今天是几号、库里有几天数据）

本项目踩的三个典型故障，恰好各打在一条上：

| 现象 | 打在哪条 | 机制 |
|---|---|---|
| "只能查最近30天" | 工具清单 | 工具里没有"任意起止日期"，只有"最近N天"一种形态 |
| "2026年5月"→"没有记录" | 工具描述 | `days` 描述写"'这个月'=30"，模型把 30 当能力上限 |
| "今年趋势"→"本月" | 系统提示词 | 提示词没写今天日期，模型靠过期的训练知识猜年份 |

**这不是模型笨，是"信息供给"和"能力供给"没给够。** 业界所有方案都在往这两个变量上使劲。

## 三、第一层解法：给"工具调用"这条路铺可靠性机器

### 3.1 原生 function calling，替换"文本 JSON 协议"

本项目协议：让 LLM 在回复**第一行输出 JSON**，再用 `_parse_tool_call` 正则式抠出工具调用。三个已知脆弱点：

- **格式失败**：LLM 先写"好的我来查……"再给 JSON、给 markdown 代码块、JSON 里带注释。
- **类型失败**：`days` 填成 `"seven"` 或 `30.0`，`**params` 直接炸。
- **偶发失败**：同一问题 10 次有 1 次格式走样——演示时最致命。

生产用模型原生 **function calling**：API 里声明工具 schema，模型返回结构化的 `tool_calls` 字段——参数必须是合法 JSON、按 schema 校验，错了把错误喂回模型自动重试。同一循环，可靠性数量级提升。

### 3.2 参数 schema 化：类型、枚举、范围、默认值

生产工具参数是 JSON Schema，不是文本描述：

```json
{"type": "object",
 "properties": {
   "store_id": {"type": "string", "enum": ["总店"], "default": "总店"},
   "days": {"type": "integer", "minimum": 1, "maximum": 150, "default": 7}},
 "required": ["days"]}
```

`enum` 堵死乱传门店 ID；`maximum: 150` 直接告诉模型能力上限——本项目"以为只有30天"的误会，本质就是能力边界没在 schema 上明示。

### 3.3 时间上下文：让模型"知道今天"或"会看表"

**模型不知道今天是几号**（训练数据截止日期是固定的）。三种解法，由简到繁：

1. **系统提示词注入**：本项目已实现（`agent_llm.py` 动态拼 `今天是 2026-08-29（星期…）`）。
2. **时钟工具**：给 `get_current_datetime()` 工具，让模型"需要时自己查"——比注入更抗污染。
3. **语义化时间轴**：工具层接受 `本月/上月/今年` 而不是让模型自己算绝对日期。本项目的 `query_new_members`"默认查本月"就属此类——**不信任模型的日期换算，把换算责任收回工具层**。


### 3.4 工具描述是一门工程

- **写反例**：`query_product_ranking` 描述里写"老板问'这个月'=30，问'昨天'=1"——比只写"查商品排名"有效得多（模型靠意图匹配，不靠语义理解）。
- **写能力边界**：描述里写"数据库保留150天，days 最大150"——模型就不会在库里有数据时说"只能查最近一个月"。**大部分"模型不会用系统"，是"系统没告诉模型自己会什么"。**

### 3.5 迭代式工具设计：靠失败喂出工具清单

> 上线 → 用户问出工具表达不了的问题 → 日志里看到 LLM 的笨拙尝试 → 新增工具/改描述 → 把问题写进 eval 集 → 回归。

本项目这几天的迭代（新增 `query_revenue_range`、`query_new_member_trend`、日期注入）就是这个流程的原样执行。这也是为什么生产团队必须给 Agent 配"日志/轨迹回放"——`run_agent(return_trace=True)` + `/api/chat` 响应的 `trace` 字段，就是为此加的。

## 四、第二层解法：语义层 + 只读 NL2SQL（范式分叉）

### 4.1 思路反转

- **工具枚举式（本项目现状）**：预判问题，把查询形状写死成工具，模型在形状里选。**问题边界 = 预判边界。**
- **数据暴露式（NL2SQL）**：把表结构 + 业务口径字典交给模型，加一个只读 SQL 执行器，让它自己写查询。**问题边界 = 数据边界。**

"2026年5月收入"在 NL2SQL 下：模型看到 `表 daily_reports: id, store_id, date, revenue...` + 口径"营收 = SUM(revenue)"，然后自己写 `SELECT SUM(revenue) FROM daily_reports WHERE date BETWEEN '2026-05-01' AND '2026-05-31'`。**只要数据里有，它就能答。**

（本项目为什么暂不启用 NL2SQL、若启用具体怎么做，见《深挖-01-NL2SQL落地设计》。）

### 4.2 语义层：防止模型"发明口径"

NL2SQL 最大风险不是 SQL 语法，是**口径被模型自作主张**。"营收"（POS 营业实收）和"会员消费"（RFM 折后金额）是两套口径。语义层把指标定义钉死：

```
营收 = SUM(daily_reports.revenue)        【别名：营业额、实收】
会员消费 = SUM(transactions.revenue)    【别名：消费额，≠营收】
新增会员 = 该月首次消费的会员数           【别名：新客、拉新】
```

模型表达意图，语义层保证口径。

### 4.3 安全机械：为什么不能裸奔

LLM 写 SQL 能写出全表扫描、缺 WHERE 的 SUM、笛卡尔积。生产必须套"监狱"：只读账号、查询超时、强制 LIMIT、结果截断、SQL 静态审查（仅 SELECT、缺 WHERE 拦截）、甚至"SQL 顾问"子 Agent 二次校验。灵活性是用安全成本换的。

### 4.4 正确姿势：混合，不是二选一

> **高频问题用固化工具（快、稳、口径可控），长尾问题用 NL2SQL 兜底（能答一切，慢、有风险）。**

本项目已有 `query_revenue_range`/`query_new_member_trend` 覆盖两个长尾方向；未来如数据量大、口径复杂化，再加只读 NL2SQL 作为第 11 个工具。

## 五、第三层解法：让它成为"生产系统"的周边机械

### 5.1 Eval：把 Agent 当测试对象

pytest 只能断言 SQL 返回，验证不了"回答质量"。Agent 行为是非确定性的——改一行工具描述可能让某问题答砸。生产方案：**黄金问题集 + 确定性断言 + LLM-as-Judge**，每次改动跑一遍，评分下降就拦下。（本项目已落地，见《深挖-02-Eval回归集设计》。）

**本项目两天踩的所有坑，本质上都是"缺 eval 的必然结果"——没有 eval，Agent 质量不可管理。**

### 5.2 Observability：把"思考过程"记录下来

日志只有 `Q: ... A: ...`，工具调用是黑盒。本项目已在 `/api/chat` 响应里加 `trace` 字段（每轮调用的工具名/参数/结果），配合 `run_agent(return_trace=True)`。生产进一步接 Langfuse / LangSmith 做轨迹回放、工具使用率统计、成本监控。

### 5.3 Guardrails + 人审：装刹车

只读 Agent 天然安全，但这是运气不是设计。一旦能写库、发消息、调外部 API：权限分层（读自动放行、写审批）、敏感操作白名单、审计日志。"自主 agent"喊得最响的场景，刹车也装得最严。

### 5.4 Memory 与 RAG：别只靠上下文窗口活着

短期记忆（会话内，本项目已有）→ 长期记忆（向量库）→ RAG 接地（业务手册、历史报告切片检索，回答引用真实资料）——**治"编造"的终极手段**。

## 六、两个新范式：MCP 与 Workflows-vs-Agents

### 6.1 MCP（Model Context Protocol）

不改变 ReAct 道路，改变**工具供给侧**：把工具封装成标准协议的工具服务器，模型客户端通过协议发现、加载、调用任意 server，生态共享（文件、数据库、飞书、GitHub…）。解决的正是"工具清单"问题的规模化版本。**本质仍是 function calling，只是把"我写的工具"升级成"标准协议的工具市场"。**

### 6.2 Workflows vs Agents（Anthropic 框架）

- **Workflow**：代码写好路径，LLM 只做路径里的步骤。本项目定时日报（`pos-daily-report`）就是 workflow。
- **Agent**：LLM 自己决定路径，动态路由。本项目"随便问"就是 agent。

细分模式：Prompt Chaining / Routing / Parallelization / Orchestrator-Workers / Evaluator-Optimizer。**大多数生产场景应优先 workflow，只有需要动态决策才用 agent。** 本项目进阶方向是混合：问题先路由（workflow），数据查询用工具（agent 循环），回答过评估器（evaluator-optimizer）。

---

## 七、真正"不同道路"的东西

自主编码 Agent（动作空间=改代码/跑测试/提 PR）、Computer-use Agent（直接操作屏幕）、Deep Research（多跳检索）、Multi-agent（角色分工）。共同点：**扩大"动作空间"，不只是"查询空间"。** 对数据分析问答这个品类，不需要上这些。

## 九、最后的大实话

1. **90% 的可靠性工作发生在模型之外。** 模型负责"聪明"，系统负责"不犯错"。
2. **"模型死板"是管理问题，不是模型问题。** 给它今天日期，它就不再算错年份；给它日期范围工具，它就不再只会查30天；把口径写进语义层，它就不再编造。**每一次"它不会"，都在告诉你一个"你没给够"的东西。**
3. **本项目四天踩的四类坑——数据层（30天聚合）、统计层（口径错误）、工具层（只会查30天）、上下文层（编0人）——就是做数据 Agent 会遇到的四类典型故障，全部修复并固化成回归用例，这是比任何名词都硬的工程履历。**
